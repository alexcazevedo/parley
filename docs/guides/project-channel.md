# Project channel

Connect a project that has its own inbox and its own staff. The project forwards what customers and staff write; parley runs the agent and pushes what the agent does back to the project, signed. Start from the variables of [setup](setup.md): `$BASE_URL`, `$TENANT_KEY` and `$AGENT_ID`. The `worker` service must be running and the model reachable (a valid model key, or [the stub](quickstart.md#try-it-without-a-model-key)). Errors, paging and limits are in [api-conventions](api-conventions.md).

Variables added here:

```
PROJECT_USER=ana
EVENTS_URL=https://inbox.example.com/parley/events
LAST_EVENT_SEQ=0
```

`$PROJECT_CHANNEL_ID`, `$EVENTS_SECRET` and `$CONVERSATION_ID` are captured with `jq` in steps 2 and 3. `$CATEGORY_ID` is captured in step 8.

Every request sends `X-API-Key: $TENANT_KEY`.

## 1. When to use it

Use an `external` channel when the project already owns the inbox, the customer channel and the people who answer.

| | Web chat | WhatsApp through Evolution | `external` |
|---|---|---|---|
| Who talks to the customer | Your client, which polls parley | Parley, through an Evolution server | The project |
| How a client learns of a reply | Polling | Parley sends it to WhatsApp | A signed push to the project, and a feed to read |
| Who answers when the agent hands off | Operators, through parley | Operators, through parley | The project's staff, in the project's inbox |
| Customer media | Image, voice note | Image, voice note | Image, voice note, PDF |

Rules for this channel:

- The project's inbox is the source of truth. Parley keeps a copy so the agent has context.
- Agent replies are text only. Parley sends nothing to the customer itself: a reply reaches the customer only when the project shows it.
- Parley's waiting lines and operator page are not used. A handoff also puts the conversation in parley's waiting line; ignore it.
- A customer is the `user_id` the project sends. It is also what the project's own MCP server receives as `parley/user_id` when the agent calls a business tool ([business-tools](business-tools.md)). A conversation is reused while it is not `CLOSED`; after `POST /conversations/{conversation_id}/close` the next message opens a new conversation with a new id. Events name the conversation, so the project keeps a map from `conversation_id` to its own customer.

## 2. Create the channel

`POST /channels` with `type` `external` and `config.events_url`, the URL that receives the pushes. Without `events_url` nothing is pushed and the project reads the feed only (step 5).

```
CHANNEL=$(curl -s -X POST $BASE_URL/channels \
  -H "X-API-Key: $TENANT_KEY" -H "Content-Type: application/json" \
  -d "{\"type\": \"external\", \"name\": \"project inbox\", \"agent_id\": \"$AGENT_ID\", \"config\": {\"events_url\": \"$EVENTS_URL\"}}" | jq .)
PROJECT_CHANNEL_ID=$(echo "$CHANNEL" | jq -r .id)
EVENTS_SECRET=$(echo "$CHANNEL" | jq -r .events_secret)
```

Expected: 201 with `id`, `type`, `name`, `agent_id`, `config`, `created_at` and `events_secret` (in `$CHANNEL`). `$PROJECT_CHANNEL_ID` is the `id`.

- `events_secret` is generated by parley, is shown only in this response and cannot be read again: store it. It signs every push (step 4). A `secret` in the create body is ignored, and `PATCH /channels/{channel_id}` with `secret` on an `external` channel is 422. There is no way to rotate it: create another channel.
- `events_url` follows the address rule of [messaging](messaging.md) step 4 (`base_url` there). It must be `http` or `https`; `localhost`, `.local`, `.localhost`, `.internal` names and private addresses give 422 `invalid events_url: ...`. A project on a private network or on the compose network lists its host in `CHANNEL_ALLOWED_HOSTS`. Every push resolves the name again and refuses a non-public address; a refused push counts as a failed try.
- To change the URL later, `PATCH /channels/{channel_id}` with `{"config": {"events_url": "..."}}`. `config` is replaced as a whole: send every key you want to keep (for example `humanize`).
- With `humanize` set in `config`, a reply is split into several short messages and each one is a separate event. See [messaging](messaging.md).

Check: `curl -s $BASE_URL/channels/$PROJECT_CHANNEL_ID -H "X-API-Key: $TENANT_KEY"` returns 200 with `type` `external`, your `events_url` in `config` and no `events_secret`.

## 3. Forward messages

`POST /channels/external/messages` takes JSON:

| Field | Required | Rule |
|---|---|---|
| `channel_id` | yes | `$PROJECT_CHANNEL_ID`. 404 `channel not found`; 422 `channel is not an external channel`. |
| `user_id` | yes | The project's id for the customer. Any string. |
| `message` | yes | Text, at most `MAX_MESSAGE_CHARS` characters (413 over it, nothing stored). |
| `message_id` | no | The project's id for this message. The same `message_id` on the same channel again stores nothing and returns `"duplicate": true`. Omitted, parley makes one up. |
| `sender` | no | `customer` (default) or `staff`. Anything else is 422. |
| `staff_name` | no | At most 120 characters. Stored with a staff message. |

Over the inbound rate limit the response is 429 and nothing is stored.

A customer message:

```
SENT=$(curl -s -X POST $BASE_URL/channels/external/messages \
  -H "X-API-Key: $TENANT_KEY" -H "Content-Type: application/json" \
  -d "{\"channel_id\": \"$PROJECT_CHANNEL_ID\", \"user_id\": \"$PROJECT_USER\", \"message\": \"Hi, where is my order?\", \"message_id\": \"in-1\"}" | jq .)
CONVERSATION_ID=$(echo "$SENT" | jq -r .conversation_id)
```

Expected: 201 with `conversation_id`, `message_id` and `duplicate` (in `$SENT`). The reply is not in the response: it arrives as an event (steps 4 and 5). While the agent is paused (below), a customer message is stored and no reply is made, and handing back does not answer it later: the agent answers only messages that arrive after the hand back.

A staff message, the project's own person writing to the customer:

```
curl -s -X POST $BASE_URL/channels/external/messages \
  -H "X-API-Key: $TENANT_KEY" -H "Content-Type: application/json" \
  -d "{\"channel_id\": \"$PROJECT_CHANNEL_ID\", \"user_id\": \"$PROJECT_USER\", \"message\": \"I am checking this for you.\", \"sender\": \"staff\", \"staff_name\": \"Rita\", \"message_id\": \"out-1\"}"
```

Expected: 201 with `conversation_id`, `message_id`, `duplicate`. What it does:

- The message is stored as an outgoing message of role `human_operator`. No agent turn runs and no `message.reply` event is recorded: the project already has the text.
- It pauses the agent for the conversation: the conversation moves to `HUMAN_HANDOFF`, and parley records `conversation.handoff` (`reason` `staff message`, `requested_by` `operator`, `brief` `null`) and then `conversation.agent` (`active` false, `cause` `staff_message`). A customer with no open conversation gets one that way.
- A staff message on a conversation that is already paused records no event. A repeated `message_id` stores nothing and records no event.
- The agent stays paused until the project hands the conversation back (step 7). There is no automatic resume.

Check: `curl -s $BASE_URL/conversations/$CONVERSATION_ID -H "X-API-Key: $TENANT_KEY"` shows `state` `ACTIVE_AI` after the first message and `HUMAN_HANDOFF` after the staff message.

## 4. Receive pushes

For each event parley sends `POST` to `events_url`, one event at a time, in order. The body is compact JSON with the keys `id`, `seq`, `type`, `channel_id`, `conversation_id`, `created_at` and `data` (the fields of each type are in step 6):

```
{"id":"2f1c0c3e-5b0e-4a53-9a41-6f3b2d6f9a10","seq":4812,"type":"message.reply","channel_id":"7d0b...","conversation_id":"c41a...","created_at":"2030-01-01T10:00:00.123456+00:00","data":{"message_id":"9e11...","seq":3,"content":"Your order left the warehouse today."}}
```

Headers:

| Header | Value |
|---|---|
| `Content-Type` | `application/json` |
| `X-Parley-Event-Id` | The event `id`. |
| `X-Parley-Timestamp` | Unix seconds when the push was sent. |
| `X-Parley-Signature` | `sha256=` and the hex HMAC-SHA256, keyed with `events_secret`, of the timestamp, a dot and the raw body bytes. |

How to receive:

1. Read the raw body bytes before parsing the JSON: the signature covers those exact bytes.
2. Verify the signature and refuse a timestamp older than 5 minutes (code below). Answer 401 on failure; parley treats it as a failed try.
3. Store the event, or queue it, and answer any 2xx within `EVENT_PUSH_TIMEOUT_SECONDS`. The response body is ignored. A redirect (3xx), another status, a timeout or a connection error is a failed try.
4. Ignore an `id` you already applied. Delivery is at least once: a push whose answer was lost is sent again.
5. Ignore an event `type` you do not know, and answer 2xx.

Verification, standard library only:

```python
import hashlib
import hmac
import time


def verify_push(secret: str, timestamp: str, body: bytes, signature: str, tolerance: int = 300) -> bool:
    """secret: the events_secret. timestamp, signature: the X-Parley-Timestamp and
    X-Parley-Signature header values. body: the raw request body."""
    try:
        if abs(time.time() - int(timestamp)) > tolerance:
            return False
    except ValueError:
        return False
    mac = hmac.new(secret.encode(), timestamp.encode() + b"." + body, hashlib.sha256)
    return hmac.compare_digest("sha256=" + mac.hexdigest(), signature)
```

Check: with a local receiver that logs the headers, send a customer message (step 3); once the agent has answered, a push arrives, `verify_push` returns `True`, and changing one byte of the body makes it return `False`.

## 5. The feed and catching up

Every event is stored in an ordered feed, pushed or not. `GET /channels/{channel_id}/events` returns them oldest first. Query: `after` (only events with a higher `seq`, default 0) and `limit` (1 to 500, default 100). There is no `X-Next-Cursor`: page with `after`. An unknown channel is 404; a channel that is not `external` is 422. Parley does not delete events.

```
EVENTS=$(curl -s "$BASE_URL/channels/$PROJECT_CHANNEL_ID/events?after=$LAST_EVENT_SEQ&limit=100" \
  -H "X-API-Key: $TENANT_KEY" | jq .)
LAST_EVENT_SEQ=$(echo "$EVENTS" | jq --argjson last "$LAST_EVENT_SEQ" '[.[].seq] | max // $last')
```

Expected: 200 with a list of `id`, `seq`, `type`, `conversation_id`, `created_at` and `data` (no `channel_id`: it is the channel you read). Repeat while the list is as long as `limit`.

- `seq` only grows within a channel. Values are not consecutive, because every channel shares the counter.
- Keep the feed position (`$LAST_EVENT_SEQ`) in durable storage and move it only when you read the feed, never when you apply a push. Applying is idempotent by `id`, so reading what a push already delivered is harmless. After a restart, an outage of the project or a deploy, read from the stored position until the list is shorter than `limit`.
- Why not move it on a push: after parley gives up on one event it pushes the later ones. A position moved by a later push skips the given-up event; the feed read from your own position returns it.

Retries:

- Parley pushes the oldest unsent event of a channel. While it waits for its next try, later events of that channel wait too.
- After the n-th failed try the next one comes after 5 seconds, 15 seconds, 1 minute, 5 minutes, 15 minutes and 30 minutes (n = 1 to 6), then 1 hour if you raise `EVENT_PUSH_MAX_ATTEMPTS` above 7. The `EVENT_PUSH_MAX_ATTEMPTS`th failure gives up. With the default 7 that is about 51 minutes of waiting, plus the time of each try.
- "Gave up" means the event is not pushed again. It stays in the feed, and the channel goes on with the next event. The worker logs `event.push_gave_up`.
- The worker checks for due pushes every `EVENT_PUSH_INTERVAL_SECONDS`.

Check: after the customer message of step 3 and one agent turn, the feed holds an event of type `message.reply` whose `data.content` is the reply, and reading again with `after` set to its `seq` returns `[]`.

## 6. Events

Every event has `id`, `seq`, `type`, `conversation_id`, `created_at` and `data`. Events exist only on `external` channels, and are recorded in the same transaction as the change they describe.

| `type` | When | `data` |
|---|---|---|
| `message.reply` | The agent's text was stored: each part of a humanized reply, the handoff text, the failure text and the unsupported-media text too. | `message_id` (the stored message id), `seq` (its position in the conversation, as in `GET /conversations/{conversation_id}/messages`), `content` (the text). |
| `conversation.handoff` | The conversation was handed to people: by the agent, by sentiment, by `POST /conversations/{conversation_id}/handoff`, or by a staff message. | `reason` (text or `null`), `requested_by` (`agent`, `system` for sentiment, `operator` for the endpoint and for a staff message), `brief` (the summary for the person who takes over; `null` for an operator handoff and when none was written). |
| `conversation.handoff_brief` | Only after `POST /conversations/{conversation_id}/handoff`: its summary was written later. The agent and sentiment paths put the brief in `conversation.handoff`. | `brief` (text). |
| `conversation.agent` | The agent was switched off or on for the conversation. | `active` (`false` or `true`) and `cause`: `staff_message`, `agent_handoff`, `sentiment`, `operator` (the handoff endpoint), `resumed` (active again) or `closed`. |
| `conversation.category` | The department of the conversation changed. | `category_id` (text or `null`), `name` (text or `null`), `source` (`agent` or `operator`). |

Order of a handoff: `conversation.handoff` then `conversation.agent` (`active` false); a handoff text, when there is one, comes after them as `message.reply`.

## 7. Hand back to the agent, and close

Hand back with `POST /conversations/{conversation_id}/resume`:

```
curl -s -X POST $BASE_URL/conversations/$CONVERSATION_ID/resume -H "X-API-Key: $TENANT_KEY"
```

Expected: 200 with the conversation, `state` `ACTIVE_AI`. Parley records `conversation.agent` with `active` true and `cause` `resumed`. A conversation that is not `HUMAN_HANDOFF` is 409 `cannot resume a conversation in state ACTIVE_AI` (or `CLOSED`). The agent answers the customer's next message, not one sent while it was paused.

Close with `POST /conversations/{conversation_id}/close`:

```
curl -s -X POST $BASE_URL/conversations/$CONVERSATION_ID/close -H "X-API-Key: $TENANT_KEY"
```

Expected: 200 with `state` `CLOSED`. From any state, including `CLOSED`. Parley records `conversation.agent` with `active` false and `cause` `closed`. The agent does not answer a closed conversation; the customer's next message opens a new conversation with a new id.

Check: after the resume, the feed has `conversation.agent` with `active` `true` and `cause` `resumed`.

## 8. Departments

Departments are categories defined in parley (see [operators](operators.md)). Define them once:

```
CATEGORY_ID=$(curl -s -X POST $BASE_URL/categories \
  -H "X-API-Key: $TENANT_KEY" -H "Content-Type: application/json" \
  -d '{"name": "billing", "description": "Invoices, payments and refunds"}' | jq -r .id)
```

Expected: 201 with `id`, `name`, `description`, `created_at`. The description is what the model reads when it picks one.

- When the agent files a conversation under a department, parley pushes `conversation.category` with `source` `agent`, and `category_id` and `name` of the department. The project shows it its own way, for example a label of that name.
- When the project's staff change the department in the project, the project tells parley:

```
curl -s -X PUT $BASE_URL/conversations/$CONVERSATION_ID/category \
  -H "X-API-Key: $TENANT_KEY" -H "Content-Type: application/json" \
  -d "{\"category_id\": \"$CATEGORY_ID\"}"
```

Expected: 200 with `category_id` and `category_locked` `true`. From now on the agent no longer picks a department for that conversation (no model call for it). `{"category_id": null}` clears it and locks too. Unknown department: 404 `category not found`. Nothing unlocks a conversation.

- That call records `conversation.category` with `source` `operator` when the department changed, so the project receives an event for its own change. Apply it like any other: the result is the same.
- With no department defined parley makes no classification call and sends no `conversation.category`.

Check: the feed has a `conversation.category` event whose `data.category_id` is `$CATEGORY_ID` and `data.source` is `operator`.

## 9. Media

`POST /channels/external/media` is a multipart form with `channel_id`, `user_id`, `file`, and optionally `caption` (at most `MAX_MESSAGE_CHARS`) and `message_id`.

```
curl -s -X POST $BASE_URL/channels/external/media \
  -H "X-API-Key: $TENANT_KEY" \
  -F "channel_id=$PROJECT_CHANNEL_ID" -F "user_id=$PROJECT_USER" -F "caption=my invoice" \
  -F "file=@invoice.pdf"
```

Expected: 201 with `conversation_id`, `message_id`, `duplicate`. The reply arrives as an event, as in step 4.

- Parley decides the type from the file's bytes and ignores the content type you send. Images: JPEG, PNG, WebP. Voice notes: Ogg, MP3, MP4 audio, WebM, WAV. PDF: a file that starts with `%PDF-`. Anything else is 415 `unsupported media content`; nothing is stored. Staff cannot send media through this endpoint.
- A file over `MEDIA_MAX_BYTES` is 413 `media exceeds max size`. Images and voice notes behave as on web chat: see [messaging](messaging.md) step 3 (transcription with `STT_MODEL`, images read when `LLM_VISION_ENABLED` is `true`).
- A PDF is a message of type `document`. The agent reads its text: the first `PDF_MAX_PAGES` pages, cut at `PDF_MAX_CHARS` characters. The model sees `<caption>`, a blank line, `[documento: <file name>]`, a new line and the text. The file name is the name of the uploaded file, cut at 120 characters (`documento.pdf` when it has none).
- A PDF with no readable text (a scan, blank, corrupt or password-protected) becomes a message of type `unsupported`. No model call is made, and the customer gets the agent's `unsupported_media_message` (the built-in text when it is not set), delivered as a `message.reply` event. Parley does not read scanned pages.
- `GET /media/{message_id}` with `X-API-Key` returns the stored file; a PDF comes as an attachment named `document.pdf`, not under its original name. The web chat upload still answers 415 to a PDF.

Check: `curl -s "$BASE_URL/conversations/$CONVERSATION_ID/messages?limit=100" -H "X-API-Key: $TENANT_KEY" | jq '[.[] | select(.media_url)]'` lists the file's message with `type` `document` (or `unsupported` for a PDF without text) and a `media_url`. Do not read only the newest message: once the turn has run, that is the agent's reply.

## 10. Try it

`examples/project_inbox/` is a small project with its own inbox, about 290 lines in one file, using only the calls of this guide. It forwards messages, verifies pushes and remembers the ids it applied. It moves its stored feed position only when it reads the feed, never on a push, and reads the feed at start, on request and on a timer, so an event parley gave up on is still found. Its `README.md` has the routes.

1. Start parley with the stub model and the example:

```
docker compose -f docker-compose.yml -f docker-compose.stub.yml -f docker-compose.example.yml up -d --build
```

2. Create the tenant, agent and channel as in steps 1 and 3 of [setup](setup.md) (the tool step is optional), and the channel as in step 2 here (not the web chat channel of setup step 4), with `events_url` set to `http://project-inbox:9200/parley/events`. The override file lists `project-inbox` in `CHANNEL_ALLOWED_HOSTS` for `api` and `worker`.
3. Give the example its variables and recreate it:

```
export PARLEY_API_KEY=$TENANT_KEY PARLEY_CHANNEL_ID=$PROJECT_CHANNEL_ID PARLEY_EVENTS_SECRET=$EVENTS_SECRET
docker compose -f docker-compose.yml -f docker-compose.stub.yml -f docker-compose.example.yml up -d project-inbox
```

The variables live only in that shell. A later `up` from a shell without the three exported recreates `project-inbox` unconfigured, so put them in `.env` (`PARLEY_API_KEY=...`, `PARLEY_CHANNEL_ID=...`, `PARLEY_EVENTS_SECRET=...`), which compose reads. The example keeps its inbox in the container's `/tmp`: it survives a restart, but removing the container (`down`, or a recreate with changed settings) loses the inbox, and the feed then refills it from the start.

4. Use it on port 9200: a customer message is answered inside its inbox by push; a staff message pauses the agent; its hand-back route resumes it; a department appears next to the customer once the project's staff move it (section 8, the `PUT` call): the stub model never picks one, as in [quickstart](quickstart.md#try-it-without-a-model-key), so with the stub only the staff move shows a department. Stop the example, send more customer messages to parley, start it again: the replies it missed arrive from the feed, each once.

The example has no media route: send media to parley directly (`POST /channels/external/media`, section 9). A message sent straight to parley, not through the example, shows in its inbox only as the agent's reply (under the conversation id, as the example never saw the customer's message).

Check: the example's inbox page at `http://localhost:9200/` shows the agent's reply under the customer's message.

## 11. The same flow for other businesses

Nothing in parley is specific to one kind of business. In each case the project forwards, receives and shows; parley runs the agent.

A store with a shared WhatsApp inbox: the store's system receives every WhatsApp message on its own numbers and forwards it with the customer's phone number as `user_id`. When an attendant answers in the store's screen, it forwards that as `sender` `staff`, so the agent stops. Each `message.reply` is sent to the customer from the store's number and shown in the thread. Departments such as sales, support and billing are categories; `conversation.category` becomes a label on the thread, and moving the label in the store's screen calls `PUT /conversations/{conversation_id}/category`. A "give back to the agent" button calls `POST /conversations/{conversation_id}/resume`.

A clinic: the reception system forwards each patient message with the patient's record number as `user_id`. Departments are scheduling, billing and exams. The agent answers questions and, when it hands off, `conversation.handoff` carries the brief so the receptionist does not ask again. A referral sent as a PDF is read as text; a photographed one is not.

A law firm: the intake tool forwards each prospective client's messages with its own client id as `user_id`. Departments are practice areas such as labor and family. The agent collects the facts and hands off with a brief to the lawyer's assistant. Contracts sent as PDF are read up to `PDF_MAX_PAGES` pages; a scanned contract gets the agent's `unsupported_media_message`.

Next: tune the agent in [agent-behaviour](agent-behaviour.md); settings in [configuration](configuration.md).
